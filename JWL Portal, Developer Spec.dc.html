1. What exists, and what it is worth

The prototype is not a mock-up. It is a functioning single-page application containing the finished interaction design, the full job lifecycle, the role model, the copy and the visual system. Every screen the developer needs to build has already been designed, reviewed and approved by the client.

The developer should treat it as the specification of record for behaviour and appearance. What it lacks is everything below the interface:

  • No server, no database. State lives in one browser's localStorage key and does not leave the device.
  • No authentication. The sign-in screen shows the flow; picking a name switches role without a credential check.
  • No enforcement. Role restrictions are cosmetic, hiding fields in the browser rather than refusing requests at the server.
  • No notifications. The WhatsApp action composes the right message and hands it to the user to send by hand.
  • No audit durability. The history panel is real in shape but is wiped with the browser store.

The commercial point: design and UX are done and paid for. This engagement is backend, security and deployment work. A developer quoting for a full product design cycle has misread the brief.

2. Recommended stack

The governing constraint is that a five-person valuation practice in Dublin must be able to keep this running for years without a retained developer. That rules out anything requiring servers to be patched, containers to be orchestrated, or a build pipeline only its author understands. Every choice below is managed, has a free or near-free tier at JWL's volume, and can be handed to another developer without archaeology.

Substituting Netlify for Vercel, or Neon plus Auth.js for Supabase, is defensible. Substituting a self-managed VPS, WordPress, or a bespoke PHP application is not.

4. Data model

Seven tables. The prototype's sample data in /jobs/index.html is the authoritative field list and should be read alongside this.

Table Contents and notes
jobsReference, address, Eircode, purpose, source, status, urgency, assignee, inspection datetime, counterparty, invoice number, invoice amount, date paid, created and updated timestamps. Status and purpose as Postgres enums, matching the prototype's twelve valuation types and nine states exactly.
clientsName, phone, email. Separated from jobs so repeat instructions link to one client, and so the personal data has its own retention and erasure boundary.
usersMirrors Supabase auth users, adds display name, initials and role. Role is an enum of owner, admin, valuer.
notesInternal commentary, author and timestamp. Editable for fifteen minutes after writing, then frozen.
audit_logAppend only, written by trigger rather than application code. Family law and probate work can end up in front of a court, so who changed what and when must be defensible.
documentsReport PDFs and site photographs in Supabase Storage, private bucket, signed URLs only. Phase 6.
notificationsOutbound queue with delivery state, so a failed WhatsApp or email send is retried and visible rather than silently lost.

Permissions belong in the database. The three roles must be enforced by Row Level Security policies on jobs, clients and notes, not by conditional rendering. Concretely: a valuer authenticating and querying the API directly must be unable to read invoice_amount or write paid_on. This is a test case, not a preference.

5. Phased plan

Ordered so that each phase ends with something demonstrable, and so JWL can stop after phase 4 with a usable system if budget requires.

Phase 1 · 3 to 4 days

Foundations

Repository under JWL's GitHub account. Next.js and TypeScript scaffold. Supabase project in an EU region. Schema and enums migrated as versioned SQL files, not clicked into a dashboard. Seed script reproducing the prototype's ten sample jobs. Vercel connected, staging and production environments split. Done when a fresh clone plus one command yields a running local instance with seeded data.

Phase 2 · 3 to 4 days

Authentication and roles

Supabase Auth with email and password, plus TOTP second factor, which the prototype's sign-in screen already promises. Invitation-only, no public registration. Password reset. Row Level Security policies for all three roles, with an automated test per policy. Session expiry and forced re-authentication for financial writes. Done when the policy test suite passes and a valuer's token is provably refused the financial columns.

Phase 3 · 6 to 8 days

The portal itself

Port every prototype screen to real components against real data: queue with its four tabs and counts, search, job detail, the eight-step progress stepper, claim, release, reassign, advance, urgency flag, lost and reopen, notes, audit history, manual job entry, and the owner's overview with its four charts and CSV export. Mobile first, since valuers use this standing in somebody's hallway. Done when the prototype and the build are indistinguishable in behaviour, screen by screen.

Phase 4 · 3 to 4 days

Website integration and email

Replace the prototype bridge in enquiry-store.js with a real endpoint. Wire the service-page forms and the pop-up. Validation, Turnstile, rate limiting, honeypot. Resend with SPF, DKIM and DMARC on the jwl.ie domain, client acknowledgement and internal alert templates. Done when a form submission on the public site appears as an unclaimed job and both emails arrive in the inbox, not the spam folder.

Phase 5 · 2 to 3 days, optional

WhatsApp notification

Twilio WhatsApp sender, Meta business verification, one approved template matching the prototype's message format. Queue with retry and a visible failure state. Done when a new urgent enquiry reaches the team group within a minute, carrying no client-identifying detail.

Phase 6 · 4 to 6 days

Hardening, launch, handover

Document storage with signed URLs. Sentry. Automated backup verification, meaning a restore actually performed once and witnessed. Accessibility pass to WCAG 2.2 AA. Penetration sanity check on authentication and the enquiry endpoint. Written runbook, environment variable inventory, and a two-hour training session with the team. Done when Shane can add a staff member, reset a password and export a month's figures without assistance.

Phases 1 to 4 give a working system: 15 to 20 days. All six: 22 to 30 days. At Dublin contract rates of €450 to €600 a day that is roughly €10,000 to €18,000, and a quote materially outside that range deserves an explanation in either direction.

6. WhatsApp, the honest version

The team's habit of coordinating on WhatsApp is a genuine requirement, but automated sending is not as simple as the prototype's share button implies, and the developer should price it with open eyes.

  • Sending programmatically requires the WhatsApp Business API through a provider such as Twilio, plus Meta business verification, which takes days to weeks and needs company documentation from JWL.
  • Business-initiated messages must use templates approved by Meta in advance. Free-form text is only permitted inside a 24-hour window opened by the recipient.
  • Posting into an existing group chat is not supported by the API. The practical patterns are a broadcast to each team member individually, or a small Twilio-owned group. Whichever is chosen, it is not literally the group they use today.
  • Client-identifying data must never appear in the notification. The prototype already gets this right, sending type, area and deadline only, and that constraint is a requirement rather than a nicety.

If verification or cost proves obstructive, the fallback is SMS through the same Twilio account, roughly €0.05 per message, no template approval, delivered instantly. The recommendation is to build phase 4's email alerts first, run for a fortnight, and decide whether WhatsApp is still wanted.

8. Data protection

The portal holds names, addresses, telephone numbers and, by implication, information about bereavement, separation and long-term care. That is sensitive in substance even where it is not special category data under GDPR, and the practice is regulated. Requirements:

  • All data resident in the EU. Database, file storage and backups.
  • Data processing agreements on file for every processor: Supabase, Vercel, Resend, Twilio, Sentry.
  • Personal data scrubbed from error reports before they reach Sentry.
  • A documented retention rule, and an implemented one. Professional indemnity practice points to holding valuation files for a defined number of years; Shane's insurer sets the number, and the developer implements whatever he specifies.
  • A subject access request must be answerable from the interface, not by a developer writing SQL.
  • The portal excluded from search engine indexing, as the prototype already does, and rate-limited against credential stuffing.

9. Handover, and what JWL must own

Payment of the final phase should be contingent on all of the following existing:

  • The repository in JWL's GitHub organisation, with full history. Not a zip file, not the developer's account.
  • Every third-party account owned by JWL, with the developer's access removable in one action.
  • An environment variable inventory naming every secret, where it lives, and how it is rotated.
  • A README that takes a competent stranger from clone to running locally in under thirty minutes.
  • Database migrations as files in the repository, so the schema can be rebuilt from scratch.
  • One restore from backup performed and witnessed before launch. An untested backup is not a backup.
  • A runbook covering the six things that will actually happen: add a user, remove a user, reset a password, the site is down, the emails stopped, a client asks for their data.

10. Out of scope

Named so that nobody quotes for them and nobody expects them: accounting integration, whether Xero, Sage or Bullet; automated valuation report generation; client-facing job tracking; e-signature; diary synchronisation with Google or Outlook calendars; Property Price Register or Tailte Éireann data feeds; a native mobile application. Each is a reasonable second-phase conversation. None is in this contract.

11. Decisions needed before work starts

  1. Is the WhatsApp notification in or out of the initial contract, given section 6?
  2. How many years are valuation records retained, per the professional indemnity policy?
  3. Does the valuer role see invoice amounts on its own jobs, or none at all? The prototype currently says none.
  4. Are historical jobs being migrated from existing spreadsheets or files, and if so how many? This is not currently costed.
  5. Who at JWL holds the account credentials and the payment card, and who is the named deputy?
